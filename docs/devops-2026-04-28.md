# inryokü — DevOps Operations Guide (2026-04-28)

This is the runbook for everything outside the application code: how to verify
a build, ship it, watch it, back it up, and roll it back. Companion to:

- `scripts/deploy-checklist.md` — the gate before every prod deploy
- `.github/workflows/test.yml` — CI on every push / PR
- `.github/workflows/deploy.yml` — deploy template (off by default)

---

## 0. Mental model

inryokü ships as a **single Node process serving static files + a small API**.
There is no build step. "Releasing" = pushing new code + bumping the
`?v=` cache-buster on assets so browsers refetch.

```
        ┌──────────────────────────────────────────────────┐
        │  GitHub  ──push──►  workflows/test.yml (matrix)   │
        │            │                                      │
        │            └──merge─►  workflows/deploy.yml       │
        │                              │                    │
        │                              ▼                    │
        │                    Render / Vercel / VPS          │
        │                              │                    │
        │                              ▼                    │
        │                    inryoku-server (node)          │
        │                     ├─ static html/js/css         │
        │                     ├─ /api/* endpoints           │
        │                     └─ data/ (subscribers etc.)   │
        └──────────────────────────────────────────────────┘
```

## 2. Pre-commit gate

Wire once per clone:

```bash
ln -s ../../scripts/precommit.sh .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

What it blocks on:

1. `npm test` failing
2. `node --check` parse error on any tracked `.js` / `.mjs` / `.cjs`
3. Unbalanced `<script>` / `<style>` tags or missing `<!DOCTYPE>` warning
4. CSS `{` / `}` mismatch
5. Invalid JSON in `manifest.json`, `i18n.json`, `package.json`
6. Likely-secret patterns (AWS access keys, OpenSSH/RSA private key headers,
   `sk-...` style tokens)

Bypass only with explicit reason: `git commit --no-verify` (don't, basically).

## 3. Releases (cache-buster bump)

The site uses query strings on every asset URL: `enhance.js?v=20260428`.
When you change an asset, bump the version so clients refetch.

```bash
# preview
npm run release:dry

# bump everything to today
npm run release

# bump to a specific date
bash scripts/release.sh --version 20260501

# bump pure-integer ?v=N → N+1 (legacy assets)
bash scripts/release.sh --integer
```

Backups of the original files go to `.release-backup/<timestamp>/` (gitignored
implicitly — feel free to add to `.gitignore`).

After bumping:

```bash
git diff           # eyeball the change
git commit -am "release: bump cache-buster $(date +%Y%m%d)"
git push
```

Service worker caching: if you changed any precached asset, also bump
`CACHE_NAME` in `sw.js` so clients invalidate the SW cache on next visit.

## 4. Environment variables

`.env` keys (current set):

| key                          | required | format                               | notes                          |
|------------------------------|----------|--------------------------------------|--------------------------------|
| `SHOPIFY_STORE_DOMAIN`       | yes      | `*.myshopify.com` or custom domain   | Storefront API host            |
| `SHOPIFY_STOREFRONT_TOKEN`   | yes      | alnum 20+                            | Storefront access token        |
| `GELATO_API_KEY`             | yes      | url-safe 20+                         | Print-on-Demand                |
| `GROQ_API_KEY`               | yes      | `gsk_...`                            | AI info chat (graceful fallback if absent) |
| `ADMIN_API_KEY`              | yes      | hex 32+ or url-safe 24+              | guards admin endpoints         |
| `NODE_ENV`                   | rec.     | `production` in prod                 |                                |
| `PORT`                       | opt.     | int                                  | default 3000                   |
| `SHOPIFY_PRODUCT_ID`         | opt.     | `gid://shopify/Product/<id>`         | for direct product links       |
| `SHOPIFY_VARIANT_ID`         | opt.     | `gid://shopify/ProductVariant/<id>`  | the launch variant             |
| `SITE_ORIGIN`                | opt.     | `https://...`                        | canonical origin (OG / sitemap) |

Validation:

```bash
npm run check:env             # against ./.env
bash scripts/check-env.sh --file .env.production --strict
```

The script **never prints values** — only the var name, length-masked, and
verdict. Safe to run in CI logs.

Where prod vars actually live:

- **Render**: service → Environment tab
- **Vercel**: project → Settings → Environment Variables
- **VPS**: `/etc/inryoku.env` (mode 0600, owned by the service user), loaded by
  the systemd unit via `EnvironmentFile=`

Never commit `.env*` (only `.env.example` if you create one).

## 5. Deploy targets

Pick **one** in `.github/workflows/deploy.yml` by flipping its `if:` to `true`
and setting the secrets.

### A. Render (recommended starter)

1. Create a Web Service from the repo.
2. Build: `npm ci`. Start: `node server.js`. Health check: `/robots.txt`.
3. Add env vars from §4.
4. Settings → Deploy Hooks → copy URL.
5. Repo Secrets: `RENDER_DEPLOY_HOOK_URL = <copied url>`.
6. Flip `deploy-render.if` to `true`.

CI on `main` will POST the hook; Render redeploys.

### B. Vercel

1. `vercel link` locally to capture `VERCEL_ORG_ID` / `VERCEL_PROJECT_ID`
   (or copy from the dashboard).
2. Generate a token: vercel.com → Account → Tokens.
3. Repo Secrets: `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`.
4. Flip `deploy-vercel.if` to `true`.

Note: Vercel runs Node functions. `server.js` works as a single Node server,
but if you want zero-config you may need to wrap routes as Vercel functions.
For a static-first MVP, prefer Render or VPS.

### C. VPS (most control)

systemd unit example (`/etc/systemd/system/inryoku.service`):

```ini
[Unit]
Description=inryoku web
After=network.target

[Service]
Type=simple
User=inryoku
WorkingDirectory=/srv/inryoku
EnvironmentFile=/etc/inryoku.env
ExecStart=/usr/bin/node server.js
Restart=on-failure
RestartSec=2
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/srv/inryoku/data /srv/inryoku/backups

[Install]
WantedBy=multi-user.target
```

Behind nginx / Caddy with TLS. Repo Secrets: `SSH_HOST`, `SSH_USER`, `SSH_KEY`
(private key, contents), `SSH_KNOWN_HOSTS` (`ssh-keyscan host`).

### Docker (any of the above)

```bash
docker compose up --build       # local
docker build -t inryoku:prod .  # build
docker run --rm -p 3000:3000 --env-file .env inryoku:prod
```

The image runs as non-root, uses tini as PID 1, and ships a wget-based
`HEALTHCHECK`. `.dockerignore` keeps tests / docs / backups / dot-files out.

## 6. Health monitoring

Local or against any environment:

```bash
npm run healthcheck                            # http://localhost:3000
bash scripts/healthcheck.sh https://inryoku.com
BASE=https://staging.example.com npm run healthcheck
```

What it checks:

- `GET /` 200 `text/html`
- `GET /robots.txt` 200 `text/plain`
- `GET /sitemap.xml` 200 `(text|application)/xml`
- `GET /manifest.json` 200 `application/(json|manifest)`
- `GET /offline.html` 200 `text/html`
- Response headers on `/`:
  - `content-security-policy`
  - `x-content-type-options`
  - `referrer-policy`
  - `permissions-policy`
  - `strict-transport-security` (https only)

External uptime: point any pinger (BetterStack, UptimeRobot, healthchecks.io)
at `/robots.txt` every 1–5 minutes — cheap and cacheable.

## 7. Backups

```bash
npm run backup
# or
bash scripts/backup.sh --out /var/backup/inryoku --keep 30
```

- tar.gz of `data/` to `backups/inryoku-data-<ts>.tar.gz`
- sha256 sidecar
- prune to last N (default 14)

**Schedule on the host** (VPS):

```cron
# /etc/cron.d/inryoku-backup
30 3 * * * inryoku /srv/inryoku && bash scripts/backup.sh >> /var/log/inryoku-backup.log 2>&1
```

**Off-host copy** is mandatory — a backup that lives only on the same VM is
not a backup. Sync the `backups/` dir to S3 / B2 / Drive nightly.

Restore:

```bash
tar -xzf backups/inryoku-data-<ts>.tar.gz -C /tmp/restore
rsync -a /tmp/restore/data/ /srv/inryoku/data/
sudo systemctl restart inryoku
```

## 8. Operational scenarios

### Scenario A — "the site is down"

1. `bash scripts/healthcheck.sh https://inryoku.com` — capture exact failure.
2. Check upstream platform status (Render / Vercel / VPS provider).
3. If Render/Vercel: redeploy previous successful build from dashboard.
4. If VPS: `sudo systemctl status inryoku && journalctl -u inryoku -n 200`.
5. If still broken in 10 min, follow rollback in `scripts/deploy-checklist.md`.

### Scenario B — "checkout is broken"

1. Verify Storefront token live: `curl -I https://$SHOPIFY_STORE_DOMAIN/api/...`.
2. `npm run check:env` against the prod env file — token format ok?
3. Reproduce against staging Shopify store with a test variant.
4. If Shopify-side (rate limit, plan issue), revert variant config in env to a
   known good variant and redeploy.

### Scenario C — "AI chat 500s"

1. Groq key valid? `npm run check:env` (format only) + try a curl with the key.
2. Quota exceeded? Switch the chat panel to fallback copy in `i18n.json` until
   quota resets — server should already gracefully degrade if `GROQ_API_KEY`
   is empty.

### Scenario D — "stale JS in browsers after deploy"

1. Confirm `?v=` was bumped: `grep -h '?v=' index.html | head`.
2. If not, run `npm run release && git commit -am 'release: bump' && git push`.
3. If yes but still cached: bump `CACHE_NAME` in `sw.js` so the SW invalidates.

### Scenario E — "rotate ADMIN_API_KEY"

1. Generate: `openssl rand -hex 32`.
2. Update prod env (Render dashboard / Vercel / `/etc/inryoku.env`).
3. Redeploy / restart.
4. `bash scripts/healthcheck.sh https://...` and exercise an admin endpoint.
5. Update password manager / shared vault.
6. Note the rotation date in `docs/secrets-rotation-log.md` (create if absent).

### Scenario F — "subscriber data loss"

1. Stop the service to prevent further writes: `sudo systemctl stop inryoku`.
2. Restore latest backup (§7).
3. Diff `data/subscribers.json` against the backup; reconcile new entries from
   logs if any landed between last backup and incident.
4. Restart: `sudo systemctl start inryoku`.
5. Healthcheck + spot-check subscribe flow.

## 9. Secrets handling

- `.env` and `.env.*` are **never committed**. CI/CD reads from platform secret
  stores; production reads from `/etc/inryoku.env` or platform env.
- `scripts/check-env.sh` is the only sanctioned way to "see" env state in
  shared logs — it never prints values.
- Rotate `ADMIN_API_KEY` every 90 days. Rotate vendor keys (Shopify, Gelato,
  Groq) on personnel changes or any suspected leak.
- `scripts/precommit.sh` greps for AWS / OpenSSH / `sk-...` shapes and blocks
  the commit if any tracked file matches.
